# 读取行

**简体中文** | [English](reading.md)

读取行有四条语句：`select one`、`select many`、`select page`、`select entity ... by id`。它们都会等待查询完成，后续语句可直接读取结果。

## 查一行

```sk
select one entity from table "users" and store the result in {_user::*}:
    where all:
        name = "Alice"
send "name: %{_user::name}%, age: %{_user::age}%"
```

每一列对应变量中的一个键，键名就是列名。`where` 块可以省略，此时由数据库决定返回哪一行。要明确指定某一行，请按主键或唯一列查询。

## 查多行

```sk
select many entities from table "users" and store the results in {_users::*}:
    where all:
        active = true
send "第一个: %{_users::1::name}%"
```

结果以从 1 开始的行号和列名为键，例如 `{_users::1::name}`。即使只匹配到一行，也会保留行号，因此 `select many` 的结果结构始终一致。`rowIndex::column` 结构没有现成的行数表达式：`size of {_users::*}` 只统计第一层的值，而每行都是子列表。请根据行号键统计行数，或自行维护计数器。

`select many` 不带 `ORDER BY`，因此哪一行位于 `::1` 由数据库决定。需要固定顺序时，请在脚本中排序；本页只有 `select page` 保证返回顺序。

## 分页

```sk
select page 2 with size 20 from table "users" and store the results in {_page::*}:
    where all:
        active = true
```

- 页码与每页大小都必须至少为 1：`page 1` 是第一页，大小 20 表示每页二十行。
- 行号从每页重新开始，`{_page::1::name}` 是**当前页**的第一行，不是整张表的第一行。
- 结果按**主键升序**返回。因此，分页需要已注册的主键，以便各后端采用一致的排序方式。
- 页码超出末页时返回空结果，不会报错。
- 每页最多 **5000 行**，超过这个大小的分页会在查询发送前被拒绝。见[一次读取最多能存多少行](#一次读取最多能存多少行)。
- 分页使用排序后的**偏移量，不是快照**。两次读取之间插入或删除行，可能使后续行的位置变化，造成重复读取或遗漏。遍历正在写入的表时，可考虑主键游标条件（`id > {_last}`），但必须同时保证按主键稳定排序；仅加这个条件并不足够，`select many` 本身不提供 `ORDER BY`。

## 一次读取最多能存多少行

一次读取最多存储 **5000 行**。超过这个数量的结果会被**拒绝**：不存储任何内容、结果变量被清空，`last database error` 会说明上限以及可以怎么做。

这个上限不是内存问题。Skript 逐下标写入列表变量，而且是在服务端线程上完成的，所以结果有多大，就直接从服务端的 tick 预算里扣多少：十万行六列的数据这样写进去，服务端会停住大约一秒，其中大部分就是写入本身。5000 行是恰好不让人察觉的上限——实测六列约五十毫秒——它也正好是一条写入语句能绑定的那批值，见 [写入行](writing.zh-CN.md#一次写入最多能发多少行)。超过一万个值的结果写入会更便宜一些：它在服务端线程之外建好、再一次挂载，实测少占约四分之一的服务端线程时间；若服务器的 Skript 变量存储与该路径所需的不同，就退回逐值写入。

5000 这个边界是**看出来的，不是照常量抄下来的**。在基准服务端上——走通用 JDBC 连接，跑它的那台机器上就是 SQLite——六列表的 100、500、1000、2500、5000 行读取都存下了要的每一行，而且每一次，语句窗口里最长的一个 tick 都没有超过一个 tick 本身的长度；同一个读取要 10000 行时什么都没存下，直接被拒绝，消息是 `select many read more than 5000 rows from table 'orm_bench_probe' and stored nothing.` 这几次读取各自让脚本付掉的墙钟在 50 到 100 毫秒之间。观察者自己的下限是一个 tick，这一点要先知道再把它读成“零开销”：同一轮里它把一个 290 毫秒的块报成 250 毫秒的超出，而比一个 tick 更小的活它什么都报不出来——见 [存一个结果要花多少](#存一个结果要花多少)。

宁愿拒绝、也不截断返回，是因为截断之后再也分不出来。脚本拿到一张表的前 5000 行之后，会继续回答它从未见过的那些行的问题，而这些答案是错的，不是缺失的。

请把结果收窄，或者一页一页地遍历：

```sk
loop 100 times:
    select page loop-number with size 1000 from table "users" and store the results in {_rows::*}:
        where all:
            active = true
    if {_rows::1::id} is not set:
        stop loop
    # ... 使用这一页 ...
```

### 存一个结果要花多少

查询在服务端线程之外执行，写入结果则不是。Skript 逐值写入列表变量，而且只能在服务端线程上做——变量名里可以嵌表达式，只有那个线程能解析它们。在插件自带的测试服务器上实测：全局变量（`{users::*}`）每个值约 1.4 微秒，临时变量（`{-users::*}`）约 1.1，局部变量（`{_users::*}`）约 1.0。六列的结果每行就是六个值，5000 行即 30000 个值，约占服务端线程 47 毫秒。**这是服务端线程上的开销，不是被拉长的 tick，两者现在对上了。**这个量级的开销装得进一个 tick 的 50 毫秒里；一个 tick 会拿它怎么样，是在基准服务端上定下来的——量的是一个**由脚本指定大小**的阻塞块，而不是插件报出来的数字。同一轮里，一个把同一个线程按住 290 毫秒的计数循环回来时是一个 300 毫秒的 tick（超出 250 毫秒），所以观察者确实看得见被拉长的 tick；约 50 毫秒的块回来是 0 到 10，空转窗口是 20，那是它自身的噪声。所以它的下限就是一个 tick：小于 50 毫秒的活，无论花多少，都拉不长一个 tick——36 到 47 毫秒的开销和被拉长的 tick 永远不会同时被观测到。本节讲的那次读取——六列 5000 行、30000 个值、走挂载路径——把每一行都存下了，墙钟 90 到 110 毫秒，最长 tick 恰好 50。花时间的是**值**，不是行：同样是 5000 行，两列的表只要约 15 毫秒。

在想办法压缩它之前，值得知道这些时间花在哪。约四分之一是持久化——把变更序列化、排进保存队列——外加写入锁和相关记账；其余是 Skript 自己的变量树，而那正是这个存储存在的意义。能搬到别处去建的只有这棵树。

**超过 10000 个值时，结果就是那样建出来的。** 树在读行的那个线程上组装好，服务端线程再一次挂载：只取一次写锁，摘掉变量原有的内容，把新的子树放进去。实测少占约四分之一的服务端线程时间——30000 个值从 47 毫秒降到 36 毫秒，9000 个值从 14.9 降到 12.8——而在阈值以下两种方式实测一样（600 个值：1.25 毫秒对 1.35）。这就是为什么要有阈值，而不是一律用同一种写法。

这条路径有前提，插件是在真实结果上确认它们，而不是假定它们：

- 只适用于**全局列表变量**。结果存进局部或临时变量时，仍然逐值写入。
- 服务器启动后**第一个**超过阈值的结果仍会逐值写入。这个做法依赖当前 Skript 的变量存储符合特定形态，插件会先用一个真实结果确认一次。
- 如果不符合——Skript 版本不同，或有别的插件替换了存储——那么每个结果都逐值写入。除此之外没有任何变化，也不需要调整任何设置。

无论走哪条路，存储的性质都保持不变：每个值的变更仍会按值到达的顺序通知持久化，所以保存下来的变量和内存里的变量不会彼此偏离。

## 按 id 查

```sk
select entity from table "users" by id {_id} and store the result in {_user::*}
```

这条语句直接按已注册的主键查找，不接受 `where` 块；没有匹配的行时，不存储任何结果。它没有正文，因此不加冒号，详见 [写入行](writing.zh-CN.md)。不带 `where` 块的 `select one`、`select many` 与 `select page` 也一样。

## where 块

`where` 块在 `where all:` 或 `where any:` 下每行写一个条件。前者要求全部成立，后者要求至少一条成立。两者都可以取反：`where not all:` 表示“至少一条不成立”，`where no any:`（或 `where not any:`）表示“全部不成立”。

```sk
select many entities from table "users" and store the results in {_users::*}:
    where any:
        name = "Alice"
        age > 30
        joined between {_from} and {_to}
```

| 条件 | 含义 |
| --- | --- |
| `column = value` | 相等。与 `null` 比较表示“是 NULL”。 |
| `column != value` | 不相等。 |
| `column > value`、`column >= value` | 大于、大于等于。 |
| `column < value`、`column <= value` | 小于、小于等于。 |
| `column between a and b` | 闭区间。 |

值可以使用表达式，例如 `arg-1`、`{_cutoff}`、`now`，在块执行时求值。

## 空结果与 NULL 列

以下两种情况都会表现为某个键未设置：

- `select one` **没有匹配的行**，因此没有存储结果。
- 匹配到的行中，**该列为 NULL**。

失败也会影响结果变量：

- **语句执行失败**，例如数据库拒绝查询或无法读取结果：变量会被清空，原因记录在 `last database error` 中。
- **语句在发送前被拒绝**，例如没有连接、表不存在、`where` 中的值不适合列类型或页码为 0：变量**同样会被清空**。每次读取只保留本次结果或空变量，不会残留上次结果。

确认查询成功后，可以检查主键等不可能为 NULL 的列，区分“没有行”和“列为 NULL”：

```sk
select one entity from table "users" and store the result in {_user::*}:
    where all:
        name = arg-1
if {_user::id} is not set:
    send "没有这个用户。" to sender
    stop
if {_user::age} is not set:
    send "这个用户没有存年龄。" to sender
```

请先用 `last database error` 判断查询是否成功。查询成功时，上面的两次检查才能区分“没有这一行”和“该列为 NULL”；空变量本身不能排除查询失败。

## 失败

读取总会等待完成，并报告失败原因。可在下一条语句中读取 `last database error`。读取也接受 `and wait`，但不会改变行为。见 [错误与等待](errors-and-waiting.zh-CN.md)。
